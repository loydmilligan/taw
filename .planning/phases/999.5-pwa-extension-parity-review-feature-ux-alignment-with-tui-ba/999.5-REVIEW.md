## Summary

Phase 999.5 Plan 03 adds five new API endpoints to `app-server.ts` (flashcards, ideas, issues, capture-idea, capture-issue), enriches `buildRecentStatus` with `topicCount`, and updates `renderer.ts` with a flashcard UI section in the Topics tab, wiki topic count in the Status tab, and URL linkification for research seeds output.

The new endpoints are well-structured: all five are auth-gated with `authorizeApp(request)` returning 401 on failure, Zod schemas validate POST bodies, and the implementation follows the established route pattern cleanly. The `topicCount` enrichment is correct. The `parseFlashcardsFromContent` parser handles Q:/A: proximity correctly (lookahead window of 3 lines).

Four warnings cover a button styling bug, an `onclick` vs `addEventListener` inconsistency, a path concatenation inconsistency, and duplicate `listWikiTopics()` calls per state request. The docs files are accurate and consistent with the implementation.

## Critical Issues

### CR-01: Stored XSS in flashcard list renderer

**File:** `src/bridge/renderer.ts:1165-1167`
**Issue:** `card.question`, `card.answer`, and `card.sourceFile` are inserted directly into `innerHTML` via string concatenation without HTML escaping. These values come from wiki markdown files on disk — files that may contain user-written content including HTML markup, `<script>` tags, or `javascript:` href values. If a wiki note contains `Q: <img src=x onerror=alert(1)>`, it renders as executable HTML in the PWA. The `loadFlashcards` function fetches from `/app/api/flashcards`, which reads the raw string from `parseFlashcardsFromContent` without sanitization.

```javascript
// Current (vulnerable):
listEl.innerHTML = cards.map((card) =>
  '<div class="surface" style="margin-top:8px"><strong>Q: ' + card.question + '</strong><div class="meta" style="margin-top:4px">A: ' + card.answer + '</div><div class="meta" style="font-size:11px;margin-top:4px">Source: ' + card.sourceFile + '</div></div>'
).join('');

// Fix — add a minimal HTML escape helper and use it:
function escHtml(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;');
}

listEl.innerHTML = cards.map((card) =>
  '<div class="surface" style="margin-top:8px"><strong>Q: ' + escHtml(card.question) + '</strong><div class="meta" style="margin-top:4px">A: ' + escHtml(card.answer) + '</div><div class="meta" style="font-size:11px;margin-top:4px">Source: ' + escHtml(card.sourceFile) + '</div></div>'
).join('');
```

Note: The same `escHtml` helper is also needed for `renderActions` (lines 1094-1102 — `item.title`, `item.detail` from server responses) and the Status tab (lines 1139-1144 — `status.mode`, `status.sessionDir`). Those are pre-existing patterns, but the flashcard renderer creates a new exploitation surface because the content originates from files rather than a server-controlled response.

## Warnings

### WR-01: Load Flashcards button missing variant class

**File:** `src/bridge/renderer.ts:899`
**Issue:** The "Load Flashcards" button uses `class="btn"` without a variant (`btn-primary`, `btn-secondary`, or `btn-ghost`). All other action buttons in the Topics tab use explicit variants (`btn-primary` for Summarize and Run Analysis, `btn-secondary` for Research Seeds). The bare `.btn` class has no background color defined — the button will render with a transparent background and no border, appearing nearly invisible in the dark UI.

```html
<!-- Current (missing variant): -->
<button class="btn" id="loadFlashcardsBtn" onclick="loadFlashcards()">Load Flashcards</button>

<!-- Fix: -->
<button class="btn btn-secondary" id="loadFlashcardsBtn" type="button">Load Flashcards</button>
```

### WR-02: Inline onclick attribute inconsistent with event listener pattern

**File:** `src/bridge/renderer.ts:899`
**Issue:** The Load Flashcards button uses `onclick="loadFlashcards()"` — an inline event handler. Every other interactive button in this file is wired via `addEventListener` in the script block. The inline `onclick` works here because `loadFlashcards` is at `<script>` block scope (not inside a closure), but it is inconsistent with the established pattern and would silently break if `loadFlashcards` were ever moved inside the `(function setupSwipe() {...})()` or similar IIFE. Also missing `type="button"` — browsers default form buttons to `type="submit"`, which could unintentionally trigger form submission if this element were ever wrapped in a `<form>`.

```html
<!-- Fix: remove onclick, add type="button", then wire via addEventListener in the script block -->
<button class="btn btn-secondary" id="loadFlashcardsBtn" type="button">Load Flashcards</button>

<!-- In script block, alongside the other event listeners: -->
document.getElementById('loadFlashcardsBtn').addEventListener('click', () => {
  loadFlashcards();
});
```

### WR-03: Path concatenation uses template string instead of path.join

**File:** `src/bridge/app-server.ts:638`
**Issue:** `collectAllFlashcards` constructs the full path as `` const fullPath = `${wikiRoot}/${relativePath}`; ``. The rest of the file consistently uses `path.join()` for path construction (e.g., lines 938, 946, 1054, 1062). The template literal form works on POSIX but would produce incorrect paths on Windows (backslash vs forward slash) and does not handle edge cases like trailing slashes in `wikiRoot`. Since `relativePath` is produced by `collectMarkdownFiles` via `path.join`, there is no traversal risk — but the inconsistency is a maintenance hazard.

```typescript
// Current:
const fullPath = `${wikiRoot}/${relativePath}`;

// Fix:
const fullPath = path.join(wikiRoot, relativePath);
```

### WR-04: listWikiTopics() called twice per /app/api/state request

**File:** `src/bridge/app-server.ts:900, 991`
**Issue:** The `/app/api/state` endpoint (line 318) calls both `buildAppActions(appState)` and `buildRecentStatus(appState, activeJobs, cleanupOldJobs)` sequentially. `buildAppActions` calls `listWikiTopics()` at line 900, and `buildRecentStatus` calls `listWikiTopics()` again at line 991 to compute `topicCount`. Both await the result independently, causing two filesystem scans per state request. If a user has many topics, this is noticeable latency, and the results can theoretically differ if a topic is created between the two calls.

**Fix:** Pass the topics list from `buildAppActions` through to `buildRecentStatus`, or compute `topicCount` at the call site in the route handler and pass it in:

```typescript
// In the /app/api/state handler:
const appState = await ensureAppState(request, options.defaultCwd);
const topics = await listWikiTopics();
const topicCount = topics.length;
writeJson(response, 200, {
  ok: true,
  topics,
  actions: await buildAppActions(appState, topics),       // pass topics
  recentStatus: await buildRecentStatus(appState, activeJobs, cleanupOldJobs, topicCount) // pass count
});
```

## Info

### IN-01: Linkification applied to already-rendered HTML may mangle escaped URLs

**File:** `src/bridge/renderer.ts:1510`
**Issue:** The research seeds linkification chain is:
1. `renderMarkdown(body.answer)` — HTML-escapes `&`, `<`, `>` first, then processes markdown
2. `.replace(/https?:\/\/.../g, (url) => '<a href="' + url + '"...' + url + '</a>')`

Because `renderMarkdown` escapes `&` → `&amp;` before the URL regex runs, any URL containing a query string parameter (e.g., `https://example.com/search?q=foo&bar=1`) will appear in the rendered HTML as `https://example.com/search?q=foo&amp;bar=1`. The regex matches this escaped form, so the `href` attribute and link text contain `&amp;` instead of `&` — the link text renders correctly (browsers decode entities in text nodes) but the `href` is technically wrong and may fail for some servers. Additionally, URLs ending with punctuation pulled from markdown prose (periods, closing parens) may be included in the match.

This is an info-level issue because the PWA is a single-user personal tool and the AI-generated research seeds output is trusted. If requirements change to untrusted or multi-user contexts, this should be addressed with a proper sanitizer.

**Fix (if needed):** Apply linkification before HTML escaping by processing the raw markdown text, or unescape `&amp;` → `&` in matched URLs before constructing the `href`.

### IN-02: appCaptureIdeaRequestSchema and appCaptureIssueRequestSchema are identical

**File:** `src/bridge/app-server.ts:151-159`
**Issue:** Both schemas are `{ summary: z.string().min(1).max(2000), note: z.string().max(2000).nullable().default(null) }` — byte-for-byte identical. This is not a bug (both fields have the same semantic meaning), but it signals that a single `appCaptureFeedbackRequestSchema` could be shared by both endpoints, reducing the maintenance surface if the validation rules ever need to change.

```typescript
// Current: two identical schema declarations
const appCaptureIdeaRequestSchema = z.object({ ... });
const appCaptureIssueRequestSchema = z.object({ ... });

// Simplified:
const appCaptureFeedbackRequestSchema = z.object({
  summary: z.string().min(1).max(2000),
  note: z.string().max(2000).nullable().default(null)
});
// Then reference appCaptureFeedbackRequestSchema in both route handlers.
```
